## 1. `xdis/xenos_ucode.py` — the Xenia-derived file

The header states (verbatim, abridged):

> All instruction encodings (enums, bitfield layouts) in this file are
> faithfully transcribed from the Xenia project's GPU microcode definitions:
> xenia/src/xenia/gpu/ucode.h, ucode.cc, shader.h, shader_translator.cc, …
> Copyright 2015-2022 Ben Vanik / the Xenia developers. All rights reserved.
> Released under the BSD-3-Clause license — see the LICENSE file in the
> Xenia repository root (reference/xenia/LICENSE) for the full text.
> Parts of Xenia's ucode.h in turn derive from the freedreno project
> (Copyright (c) 2012 Rob Clark, MIT license).

**Assessment:** the attribution itself is good — names the exact source
files, the copyright holder, the license, and the upstream-of-upstream
(freedreno/MIT). Two gaps:

1. **The pointer dangles in the public repo.** `reference/` is gitignored, so
   `reference/xenia/LICENSE` will not exist for anyone who clones us. BSD-3
   condition 1 requires redistributions of source to *retain* the copyright
   notice, the list of conditions, and the disclaimer. The copyright notice
   is retained; the conditions and disclaimer are referenced but not shipped.
   **Fix:** add a `THIRD_PARTY_NOTICES.md` (or `LICENSES/` directory)
   containing the full Xenia BSD-3 text (verified present at
   `reference/xenia/LICENSE`, "Copyright (c) 2015, Ben Vanik. All rights
   reserved.") and the freedreno MIT notice, and repoint the header at it.
2. Whether a Python *transcription* of bitfield structs is a derivative work
   at all is debatable (encodings are facts about hardware), but we don't
   need to litigate it: complying with BSD-3 costs one file and is the
   respectful move toward the project this toolchain owes the most.

`xdis/container.py` and `xdis/container_emit.py` cite libxenon `xe.c`/`xe.h`
and XenosRecomp as *documentation* of a format (structure layouts re-derived,
no code copied) — independent reimplementation, no license obligation, but
courteous mention in the notices file is recommended anyway.

## 2. License for our original code — recommendation

Everything except `xenos_ucode.py`'s tables is original: `xasm/` (encoders,
Program builder, combiner compiler), `xcomb/` (C99 port of our own Python),
`xdis/` drivers, examples, tests, demo app sources. **Nothing currently
declares any license** — strictly, that's "all rights reserved," which would
make the release pointless. A LICENSE file is mandatory before push.

Recommendation: **MIT or BSD-3-Clause for the whole repo** (single license,
one decision). Tradeoffs:

| | MIT | BSD-3-Clause | (GPL, for contrast) |
|---|---|---|---|
| GPL-compatible (mupen64-360 etc. can embed `xcomb.c`) | yes | yes | yes, but forces it |
| Matches our biggest dependency | XenosRecomp is MIT | Xenia and libxenon are BSD-3 | nothing we use |
| Embedding `xcomb.c` in closed/other-license homebrew | yes | yes | no |
| No-endorsement clause | no | yes | no |

Both MIT and BSD-3 satisfy the adoption goal (GPL projects like mupen64-360
can take `xcomb.c` wholesale; non-GPL homebrew can too). BSD-3 has the mild
aesthetic advantage of matching Xenia + libxenon, making the whole stack
license-uniform; MIT matches XenosRecomp and is the more conventional 2026
default. **Either is correct; do not pick GPL** — a copyleft toolchain whose
generator code is meant to be vendored into other projects' runtimes would
re-create the exact adoption barrier this project exists to remove.

Also add one explicit sentence to the LICENSE or README: **shader containers
produced by the toolchain belong to whoever runs it** (no obligations attach
to output), so nobody has to wonder.

## 3. `corpus/` — XDK compiler output used as test vectors

This is the one genuinely unresolved question. Stating it plainly:

- `corpus/vs0.bin`, `ps_fb0.bin` were extracted (by
  `xdis/extract_corpus.py`) from `mupen64-360`'s `source/shaders.S` — a GPLv2
  repo — but the bytes themselves are **output of Microsoft's XDK D3DX
  shader compiler** (version string `2.0.11626.0` embedded in the blobs).
- `corpus/cube_vs.bin`, `cube_ps.bin` are the `.vsu`/`.psu` blobs shipped
  with libxenon's BSD-licensed cube example (XDK `2.0.7680.0` vintage); the
  example's own README says they were compiled with a third-party wrapper
  around Microsoft's XNA shader compiler.

### 3.1 Why GPL/BSD labels don't settle it

mupen64-360 cannot genuinely GPL bytes Microsoft's compiler emitted, and
libxenon cannot genuinely BSD them. The honest description is: **these are
compiler-output artifacts of disputed provenance that the entire 360 homebrew
scene has redistributed openly since ~2009–2011** (in exactly those two
repos, on GitHub, unchallenged for 15+ years). Compiler output is generally
not considered a work owned by the compiler's vendor (cf. GCC's explicit
runtime exception existing only because GCC *injects* runtime code — D3DX
injects nothing comparable into shader microcode; the creative content is
the HLSL, which for the cube pair is BSD and included).

### 3.2 Options

- **(a) Keep, with a provenance note — recommended.** They are 4 small test
  vectors (~1.3 KB total), essential to the validation story (byte-exact
  round-trip against *real* XDK output is the toolchain's core credibility
  claim), already public in the upstream repos for over a decade, and used
  here under the most defensible purpose there is: interoperability testing.
  Add `corpus/README.md` stating exactly what each file is, where it came
  from, and that we'll remove on request from a rights holder.
- **(b) Exclude, ship regeneration instructions.** `extract_corpus.py`
  rebuilds `vs0.bin`/`ps_fb0.bin` from a mupen64-360 clone in one command;
  the cube pair is a two-file copy from a libxenon clone. Costs: a fresh
  clone can't run `tests/test_container_regen.py` / `test_exact_total.py` /
  `tools/gen_templates.py` without a manual step, and the golden files in
  `tests/golden/` (derived from the blobs) would have to go too.

Recommendation: **(a), plus the regeneration instructions from (b) inside
`corpus/README.md`** — so if anyone ever objects, removal is one `git rm`
with no loss of reproducibility. This is a user decision; flagging it as the
release's one open legal question.

### 3.3 Derived artifacts

`corpus/*.dis` (our disassembly), `corpus/*.recomp.hlsl` (XenosRecomp's
output), `tests/golden/*.pretty.txt` follow whatever the blobs decision is.
`corpus/cube_*.hlsl` are different: BSD example *source* code copied from
libxenon — keep, with an attribution line added at the top of each.

### 3.4 `xcomb/xcomb_templates.h`

Contains ~30 instruction-field values extracted from two corpus instructions
(one ALU mov, one tfetch2D) — i.e., numeric register/bitfield settings, not
expressive content. Risk assessed as negligible; the file already documents
its provenance. No action beyond the corpus note.

## 4. Demo apps and libxenon — finding contradicts the plan's assumption

`PLAN.md` (risk #4) and project memory treat libxenon as GPL. **The repo says
otherwise:**

- `reference/libxenon/libxenon/LICENSE`: BSD-3-Clause, "Copyright (c) 2009,
  free60.org" (+ a Broadcom copyright for the USB stack, same BSD terms).
- `reference/libxenon/devkitxenon/LICENSE` (verbatim): *"there's some stuff
  stolen from devkitPRO …, mainly makefile magic. so the makefile stuff is
  GPLed. libxenon, of course, is not; that one is BSD. example codes are BSD
  as well."*

Consequences:

- **Demo ELFs (`app/*/*.elf32`) statically link a BSD-3 library**, not a GPL
  one. Distributing the binaries requires only reproducing libxenon's
  copyright notice + disclaimer in accompanying materials (the notices file
  covers this). No copyleft, no source obligations beyond what we ship
  anyway.
- The app Makefiles `include $(DEVKITXENON)/rules` — the GPL'd devkitPRO
  "makefile magic." Our Makefiles are conventional devkitPRO-template
  derivatives; the template itself ships with every devkitPRO-style toolchain
  and *using* a GPL build system does not affect the license of what it
  builds. If we want to be maximally clean, note in the notices file that
  `app/*/Makefile` follow the devkitPRO template (GPL); they never enter a
  user's runtime.
- The toolchain proper (`xdis`/`xasm`/`xcomb`) links nothing and is
  unaffected under any reading.

## 5. `reference/` clones — not shipped (verified)

`.gitignore` line 1 is `reference/`; `git ls-files` confirms **zero tracked
files** under it. The four clones (xenia BSD-3, XenosRecomp MIT, libxenon
BSD-3/GPL-makefiles, mupen64-360 GPLv2-sourced with no top-level license
file) stay local. Several of our file headers and docs cite paths under
`reference/` as *evidence pointers* — acceptable, but the README/docs should
say once that `reference/` means "clone these yourself" (the audit-fix in §1
removes the only *load-bearing* dangling pointer).
